# Архитектурный манифест «Тёплый Дом»: взгляд на систему

Что можно сказать про решение текущей задачки: для маленькой команды из 5 человек система получается достаточно сложной, но необходимой для того, чтобы всё работало корректно.

Ниже собраны основные идеи, обоснование выбранных подходов и рефлексия над проектированием.

---

## 1. Взгляд на архитектуру и масштабирование

В ходе анализа современных подходов к IoT-системам получившаяся схема выглядит жизнеспособной и хорошо описывает ключевые концепции. В реальности система, конечно, обрастёт дополнительной бизнес-логикой, но заложенная структура позволяет:
* Легко добавлять новые микросервисы и функциональные домены.
* Эффективно масштабировать отдельные компоненты.

> **О базах данных:** 
> Раздельные базы данных для каждого микросервиса (Database per Service) — концепт, который редко встречается в чистом виде на практике в небольших проектах, но на бумаге это классический паттерн слабой связанности. Для телеметрии нам в любом случае требуется специализированное решение (например, Time-Series БД), отделённое от основной реляционной БД для SaaS-нужд.

## 2. Обоснование технологических решений

### Асинхронность и очереди событий
Специфика телеметрии и потребность в асинхронной обработке процессов логично привели к выбору **Apache Kafka** в качестве основной шины событий. Поскольку наше приложение не перегружено жесткими финансовыми транзакциями, разработчики избавлены от необходимости реализовывать сложные распределенные транзакции (Saga и т.д.), что сильно облегчает разработку.

### Выбор API (REST vs gRPC)
Разные подходы к API продиктованы характером взаимодействия:
* **REST** — традиционный, простой и понятный выбор для взаимодействия веб-клиентов с серверами.
* **gRPC** — отличный инструмент для внутренних синхронных межсервисных запросов, хотя при необходимости его можно заменить на классический REST.
* **События (Kafka)** — идеальный целевой сценарий, но синхронные вызовы «здесь и сейчас» всё равно остаются необходимыми.

### Локальный Хаб (Edge vs Cloud)
Внедрение локального менеджера (Хаба) в доме — это самое логичное решение, позволяющее не перегружать облако миллионами мелких запросов:
1. **Безопасность:** критически важные функции (управление дверьми, светом, замками) остаются внутри локального периметра, а не делегируются на внешний аутсорс в облако.
2. **Экономия:** такой подход существенно снижает чек на обслуживание облачной инфраструктуры.

### Динамика телеметрии
Телеметрию на первых этапах можно упростить. Нет строгой необходимости сохранять (сейвить) показания в режиме онлайн каждую долю секунды. Достаточно опрашивать датчики с большим интервалом или по запросу пользователя. Терабайты ежесекундных данных о температуре нужны только для аналитики и глубоких бизнес-исследований.

### Использование DDD
Попытка применить подход DDD (Domain-Driven Design) не только как продуктовый концепт, но и на уровне кода, оказалась удачной. Доменные события естественным образом ложатся на асинхронную событийно-ориентированную архитектуру.

## 3. Возможности для упрощения (MVP)

Хотя общая схема выглядит масштабной, для команды из 5 разработчиков (особенно с поддержкой современных ИИ-ассистентов) она вполне реализуема за приемлемые сроки. На первых этапах проект можно значительно упростить:
* Использовать единую общую базу данных с логическим разделением.
* Отказаться от gRPC в пользу REST для межсервисного общения.
* Отказаться от непрерывной онлайн-телеметрии в пользу периодических опросов.

## 4. Рефлексия и комментарии к процессу проектирования

1. **Диаграммы кода (Code C4):** Не совсем понятно, какую задачу решает детальное построение диаграмм классов/пакетов на этапе проектирования. Кажется, что для старта разработки диаграммы компонентов (Components C4) более чем достаточно.
2. **Ручное проектирование контрактов API в 2026 году:** Зачем писать схемы API вручную? Главная сложность лично для меня — убедиться, что созданная схема консистентна и корректно стыкуется с остальными частями проекта. С одной стороны, архитектор должен держать всю систему в голове, но с другой — остро не хватает ИИ-инструментов, которые бы автоматически проверяли взаимное соответствие контрактов.
3. **Роль архитектора в эпоху ИИ:** Как подобные архитектурные задачи будут решаться в будущем вместе с ИИ? Роль человека явно меняется. Хочется понять, какие скиллы сделают архитектора незаменимым и как их прокачать, если ИИ уже сейчас отлично генерирует правдоподобные схемы и может проводить их базовый ревью.
